# SDD：规格驱动开发流程

本目录存放 SeekFlux 的规格驱动（Spec-Driven Development）变更记录。所有结构性、契约性或跨模块的改动必须走完三个门禁，不允许直接从想法跳到代码。

## 1. 三阶段与门禁

| 阶段 | 产物 | 回答的问题 | 通过条件 |
| --- | --- | --- | --- |
| Gate 1 规格 | `SPEC-NNN-<slug>.md` | 为什么要改、改成什么样算完成、什么不做 | 需求可逐条验收；待决事项已拍板 |
| Gate 2 方案 | `DESIGN-NNN-<slug>.md` | 用哪种结构实现、为什么不用其它方案、如何回滚 | 选中方案与规格逐条对应；影响面清单完整 |
| Gate 3 任务 | `TASKS-NNN-<slug>.md` | 拆成哪些可独立验证的步骤、每步的完成证据 | 每个任务有验证命令与预期输出；顺序无环 |

只有上一阶段通过评审，才创建下一阶段文件。**规格未通过时不要写方案，方案未通过时不要写任务，任务未通过时不要动代码。**

## 2. 命名与编号

```text
docs/sdd/
├── README.md                       # 本文件：流程与模板约定
├── SPEC-001-<slug>.md              # 阶段一：需求规格
├── DESIGN-001-<slug>.md            # 阶段二：技术方案
└── TASKS-001-<slug>.md             # 阶段三：任务拆分
```

- 编号三位递增，一次变更使用同一编号贯穿三份文档。
- `slug` 使用小写短横线英文，与分支名保持一致。
- 历史文档不删除、不重写结论；被推翻的决策在文档末尾追加"修订记录"。

## 3. 与仓库既有文档的关系

SDD 文档只描述**一次变更**。项目长期事实仍由以下文件承担，本目录不复制它们：

| 文档 | 职责 |
| --- | --- |
| `SeekFlux.md` | 目标产品与长期架构 |
| `docs/module-boundaries.md` | 当前依赖边界（必须与代码一致） |
| `docs/adr/` | 已生效的长期架构决策 |
| `docs/learning/` | 交付进度与按序实现日志 |
| `contracts/` | API、事件、特征契约 |
| `evals/` | 检索与 Agent 效果基线 |

变更落地后，上述文件按 `AGENTS.md` 同步；SDD 文档只在末尾记录"落地结果"与指向它们的链接。

## 4. 规格模板要点

一份可评审的 SPEC 至少包含：

1. **现状度量**：能被执行命令复现的数字，不接受"感觉很多"。
2. **问题陈述**：每个问题附路径或命令证据，一条问题一个编号。
3. **目标与非目标**：非目标要写清楚，否则评审无法界定范围。
4. **需求列表**：编号、陈述、验收标准、当前值、目标值。
5. **验收门禁**：可执行的命令与预期结果。
6. **约束与风险**：不允许破坏的既有事实。
7. **待决事项**：需要决策人拍板的问题，逐条给出选项与建议。

## 5. 评审检查表

- [ ] 每条需求都能用一条命令或一个测试判定真假
- [ ] 问题证据可复现，没有依赖主观判断
- [ ] 非目标明确，没有"顺手也改一下"的空间
- [ ] 待决事项有明确选项，不把选择题留给实现者
- [ ] 没有把目标架构写成当前能力
