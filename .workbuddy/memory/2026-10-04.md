# 2026-10-04

## 纠正：「半步检查点」是自造词，勿再使用

前几轮我用了「半步检查点」这个说法，**代码里没有这个概念**，会误导人理解成「只存了一半的快照」。准确表述是「检查点的 boundary 字段」。

**用户提出的正确质疑**：恢复不是从持久化日志得到所有信息吗？「半步检查点」是什么？
**答案**：事件流 append-only 只记「发生过什么」，**记不出「程序现在停在哪」和「副作用发生没有」**。三类事实正交，缺一不可：

| 来源 | 表 | 能推出什么 | 推不出什么 |
|---|---|---|---|
| 会话历史 | `workspace_events` | 完整消息序列（纯 reducer 重放） | 消息外的执行位置 |
| 检查点 | `runtime_checkpoints` | nextStep / 剩余预算 / messageCutoff 游标 / 冻结的 toolSchemaVersions / completedInvocations 去重 | ——（日志推不出这些） |
| 工具日志 | `tool_call_journal` | 每个 toolCall 的 status 与 observation | ——（日志推不出这些） |

**`RuntimeCheckpoint`（13–34 行）字段性质拆分**：大部分是「位置与约束」而非内容——`nextStep`（从第几步继续）、`remainingBudgetMillis`（预算重算，挂起期间墙钟不计）、`messageCutoff`（事件流读取游标）、`definition.toolSchemaVersions()`（冻结工具版本，恢复时 `tools.require(name, frozenVersion)` 校验漂移）、`completedInvocations`（防重复派发同组合参数）、`toolCallCount`。内容类只有 `observations`/`messages`/`terminalResult`。
`savePreTurn`(2099) 传 terminalResult=null，`saveWait`(2179) 传 result → **同一字段挂起时才有值**（这就是我误称「半步」的地方）。

**关键推论：事件流推不出「决定调用」与「调用成功」的区别** —— 这正是 tool_call_journal 独立存在的原因。

**为什么必须一个事务写三份**（各层不可妥协）：
- 缺 checkpoint → 不知从哪继续、不知在等什么
- 缺 journal WAITING → 不知工具跑没跑过 → **可能重复执行副作用**；且 `suspendWait` 的 SQL 把 fencing 校验写进 `EXISTS(SELECT 1 FROM agent.sessions WHERE active_fencing_token=:token AND status='EXECUTING')` —— **条件更新是仲裁原语，append 做不到**
- 缺 runtime_waits PENDING → 不知在等谁等多久，审批卡推不出去、超时扫描找不到目标

**崩溃残留处理**：`commitResume` 第一件事把残留 `EXECUTING` 刷成 `UNKNOWN` —— 进程死在「标记开始执行」与「记录结果」之间时永远无法确定工具成没成，这信息只能存在**不会因覆盖而丢失**的地方（journal 是累积的，checkpoint 是被覆盖的当前状态）。

**WAITING 为何不是失败**：「等待外部输入」是 Agent 的合法状态之一，非异常处理。挂起与完成是并列的两种「本次执行结束」，只是后者需用户再叫醒。
