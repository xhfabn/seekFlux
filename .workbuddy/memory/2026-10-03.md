## 梳理 agent-runtime 异步审批（HITL）流程

只读排查，未改代码。结论要点（供后续复用）：

- 核心范式是「挂起并持久化 → 返回终态 WAITING」，**不持有内存 Future/线程**；用户决策走幂等 resolve 接口，再启动一次全新 run 从 Checkpoint 恢复。
- 关键入口：
  - `domain/service/runtime/AgentRuntime.java` — `prepare()` 判定 approvalReason（policy NEED_APPROVAL 或 `AgentTool.approvalRequired()`）；`approvalWait()` 造 `WaitState.Hitl`；`saveWait()` 单事务 suspend；`resumePendingTools()` 恢复后用原 toolCallId 执行一次。
  - `domain/service/execution/SessionExecutor.java` — `resumeWait()` 拿 authority → `resolveWait()` → `run(RECOVERED)`；`executeSegment()` 里 `commitResume` 决定 `ResumeAction`。
  - `domain/model/wait/` — `WaitState`（sealed，5 种 wait 类型）/ `WaitResolution`（resolutionId 是幂等键）/ `WaitRequest`。
  - 持久化实现：`platform/persistence/.../JdbcAgentRecoveryStore.java`（`suspendWait` / `resolveWait` / `commitResume` / `applyWaitResolution`；APPROVED→journal 回 DECIDED，COMPLETED→直接合成 ToolResult）。
  - 超时兜底：`domain/service/wait/WaitTimeoutProcessor.java`，确定性 resolutionId，竞态由 DB 仲裁。
- 设计依据：`docs/adr/ADR-012-agent-durable-wait-and-resume.md`；契约 `contracts/events/agent-wait-lifecycle-v1.schema.json`、`contracts/openapi/seekflux-v1.yaml` 的 `/v1/agent/sessions/{sessionId}/waits/{waitId}:resolve`。

## 追加：状态机与数据流转的精确事实

**五套并行状态机**（同一个 turnId 串起来，各自落库）：
- Session 投影 `AgentSessionStatus` IDLE/EXECUTING/SUSPENDED/COMPLETED → `agent.sessions.status`
- Run 终态 `AgentTerminalState`（含 WAITING）→ `agent.runs.state` + checkpoint.terminalResult
- 恢复边界 `CheckpointBoundary` PRE_TURN/POST_TURN/COMPLETED/SUSPENDED → `agent.runtime_checkpoints.boundary`
- 工具日志 `ToolJournalStatus` DECIDED/EXECUTING/UNKNOWN/WAITING/SUCCEEDED/FAILED/CANCELLED/TIMED_OUT → `agent.tool_call_journal.status`
- 等待单 status PENDING/APPROVED/DENIED/COMPLETED/TIMED_OUT/CANCELLED/FAILED → `agent.runtime_waits.status`

**关键不变量**（构造器 + DB CHECK 双重保证）：
- `AgentRunResult`：`state==WAITING` ⟺ `waitState != null`
- `ToolCallJournalEntry`：`status.terminal() == (observation != null)`
- `agent_runtime_wait_resolution_shape_check`：PENDING 时 resolution_id/resolution 必须都 NULL，非 PENDING 必须都非 NULL
- 唯一索引 `agent_runtime_wait_one_pending_per_session_idx`：一个 session 最多一个 PENDING wait（这就是"一次只允许一个待审批调用"的真正保证，在 DB 层而非应用层）
- 唯一索引 `agent_runtime_wait_resolution_id_idx`：resolutionId 全局唯一

**幂等键设计**：
- `WaitResolution.sameDecisionAs` 比较 schemaVersion+resolutionId+waitId+sessionId+requestId+turnId+outcome+output+errorCode+resolvedBy，**故意不含 resolvedAt**
- `appendWaitResolvedEvent` 的 eventId 优先用 `UUID.fromString(resolutionId)`，非法则 `nameUUID("wait-resolution:"+resolutionId)` —— 允许回调方自定义幂等键
- `appendOutcome` 在 WAITING 时用 `waitState.waitId()` 作 outcomeIdentity，其它终态用 `outcome:{sid}:{rid}`

**fencing token 贯穿全链**：`authorityStore.acquire` → `facts.lock(sessionId, fencingToken)` / `assertAuthorityForWait` / suspendWait 的 SQL 里 `EXISTS(session.active_fencing_token = :token AND status='EXECUTING')`。TTL 30s，定时续约，失败即 cancel(AUTHORITY_LOST)。

**恢复判定树**（`JdbcAgentRecoveryStore.commitResume` 137–187）：残留 EXECUTING→UNKNOWN → 读 checkpoint → 校验 turnId → 若 SUSPENDED+WAITING 查 runtime_waits（缺且 FAIL_FAST 抛/TOLERATE 则 WAIT_FOR_EXTERNAL，仍 PENDING 也 WAIT_FOR_EXTERNAL）→ terminal 非 WAITING 型则 COMMIT_TERMINAL → POST_TURN → 当前 step 有 UNKNOWN 且 !safeToRetry 且无 ledger 则 FAIL_UNSAFE_PENDING_TOOL → 有条目则 RESUME_PENDING_TOOLS → 否则 RESUME_PRE_TURN。

**上下文恢复实体**：`RunState` 构造器从 checkpoint 灌 steps/messages/llmUsage/observations/completedInvocations/nextStep/toolCallCount；预算用 `restored.remainingBudgetMillis()` 重算 deadline，挂起期间墙钟不算。

**`AgentSessionStatus.IDLE` 的精确语义**（`AgentSession.java` 80–149 的 reducer）：
- 只有 `WorkspaceEvent.SessionCreated` 会 yield IDLE，DB 里 `sessions.status DEFAULT 'IDLE'`。**一旦离开 IDLE 就再也回不去**（单向状态）。
- IDLE 与 COMPLETED 在 reducer 里被同等对待：148 行 `temporarilyPending = status == COMPLETED || status == IDLE ? Set.of() : toolCalls` —— 这两个状态下不检查「每个 assistant tool call 必须有恰好一个 tool result」。
- 容易误解的点：`RunCompleted` 且 state==NEED_CLARIFICATION 时投影为 **SUSPENDED 而非 COMPLETED**（140–143），所以 SUSPENDED 的准确含义是「本段没完，在等外部输入」，既包括 durable wait 也包括要澄清。`RunCancelled`/`RunFailed` → COMPLETED。
- reducer 全表：ExecutionRecorded/QueuedUserMessage/AssistantMessage/ToolResultMessage/StatePatched/CapabilitiesChanged 都是 `yield status`（不改状态），真正改状态的只有 SessionCreated/UserMessage/WaitSuspended/WaitResolved/RunCompleted/RunCancelled/RunFailed。

**五层状态机的职责归属**：
- 会话层（sessions.status）= 准入判断：能不能接新消息、要不要排队
- 运行层（runs.state + checkpoints.boundary）= 这一段的结果 + 恢复起点
- 工具层（tool_call_journal.status）= 副作用事实：工具到底跑没跑、能不能重放（`safeToRetry` 只对 READ_ONLY/IDEMPOTENT 为真）
- 仲裁层（runtime_waits.status）= 竞态裁决：谁先写谁赢

## 追加：为什么仲裁层必须 UPDATE、为什么审批只能单批

**问题一：为什么 runtime_waits 用条件更新而不是纯 append**

`resolveWait`（`JdbcAgentRecoveryStore` 377–434）是 `@Transactional`，**一次决议同时写三处**：
1. `UPDATE runtime_waits ... WHERE wait_id=? AND status='PENDING'` — 仲裁
2. `UPDATE tool_call_journal ... WHERE status='WAITING'` — 工具状态推进（`applyWaitResolution`）
3. `APPEND workspace_events` — 审计（`appendWaitResolvedEvent`）

不是二选一，而是历史事实与仲裁事实的存储要求相反。append-only 撑不起仲裁的三个硬需求：
- `SELECT ... FOR UPDATE`（381 行）+ `WHERE status='PENDING'` 把读-判断-压成一个不可分割操作，纯 append 下竞态窗口无法消除（三个并发请求都能 append 出互相矛盾的决议）。
- `agent_runtime_wait_one_pending_per_session_idx` 是 `ON (session_id) WHERE status='PENDING'` 的**部分索引**——只有 status 是「当前值」而非「历史」时该谓词才成立。
- `agent_runtime_wait_resolution_shape_check`（PENDING ⟺ resolution 字段全 NULL）是对单行当前值的形状约束，append 快照模型里没有「全空」这个状态。

结论：**append-only 适合记录发生过什么；仲裁需要的是「当前归谁」，天生是可变单值。** 两者混在一张表会互相污染，故 ADR-012 §9 三层分离。决议记录写完不删也是为了给 `sameDecisionAs` 幂等判定留依据——用存储换正确性。

**问题二：为什么一次只允许一个待审批调用**

`AgentRuntime` 425–430 的限制比预期更严：是 `prepared.size() != 1 || approvalCalls.size() != 1`——模型输出 3 个工具、其中 1 个要审批，整个 turn 直接 `MULTIPLE_TOOL_APPROVAL_UNSUPPORTED` 失败。

根因不在 DB，在 LLM 协议：**assistant 消息里 N 个 tool_call，下一条必须给出恰好 N 个 tool_result**，部分完成的消息非法。三处代码证据：
- `AgentSession.restore` reducer 除 IDLE/COMPLETED 外都校验「每个 tool_call 恰好一个 result」，不通过直接丢弃事件。
- `applyWaitResolution` 的 APPROVED 分支把 journal 从 WAITING **改回 DECIDED**（不是前进），因为「批准只是解锁，执行由恢复后的模型 loop 重新驱动」。
- 只有非 APPROVED 的 outcome 能**凭空合成** `AgentToolObservation` 补齐结果，且补的只能是终态失败/已完成，不是「部分成功」。

若要支持批量审批需改动 6 处：唯一索引（一会话 1 个 PENDING → N 个）、`WaitState.Hitl` 单数字段、`saveWait` 的 checkpointId 精确匹配、`applyWaitResolution` 批量聚合、`resumePendingTools` 两态区分、reducer 配对校验。**最后一条是死结**。

可行的替代方案：
- **A（推荐）**：不改审批语义，让模型一次只调一个——把 `MULTIPLE_TOOL_APPROVAL_UNSUPPORTED` 硬失败改为「截断为第一个 + 其余回填失败结果」，模型下一轮自重试。
- **B**：引入 `WaitState.HitlBatch`，对外 N 个独立 wait（各自 timeout / duplicate 判定），内部串行复用现有 `resolveWait`，**恢复点仍只有一个 checkpoint**，journal 侧等决议收齐后一次性补 ToolResult。
- **C**：改协议允许 tool result 延迟——需改模型侧训练/推理假设，不现实。

设计洞察：若 Agent 经常需要「同时批多个」，问题在**工具粒度**而非审批机制，正确解法是让工具支持批量（`publishBatch(items[])`）。

## 待确认 / 下次可跟进

- HITL 的「选项」目前只由 `WaitState.Hitl` 的 toolName + reason + proposedArguments + deadlineAt 表达，runtime 内没有独立的 options 结构；若产品需要「修改参数后批准」，需要在 resolution 之外扩 `MODIFY` 语义。
- `executeSegment()` 里 resume 走 `IngressCommitResult.RECOVERED` → `ResumeSource.CRASH_RECOVERY`，没有用 `HITL_CALLBACK`；目前 `ResumeSource` 在 JDBC `commitResume` 中未被消费，但语义标注不准，值得单独确认。

## 追加：多审批的真相与「审批卡会不会丢」

**先纠正前两轮的两处表述不准**：
1. 这个 Runtime **支持多个审批**——支持的是「跨轮串行」：主循环 `for (step = startStep; step <= maxSteps; step++)` 每步只处理一批 tool_call，挂起是 return，恢复后重新进同一个循环。step1 批 publish → 跑完 → step2 又批 transfer，完全合法、原生支持。真正不支持的只有「单轮内批量并发」。
2. 协议禁止的是**部分批准**，不是批量审批本身。客户端收齐 N 个决议后一次性提交（各自独立 resolve、各自独立 timeout）是可行的。

**审批卡不会丢，现状已实现用户设想的「恢复时重新给客户端」**：
- `AgentSession.snapshot()` 264–269 行把 `pendingWait` 对应的 `WaitSuspended` 事件位置显式加进 `retainedEventPositions`，该事件永久留在事件流里不被清理。
- `pendingWait()`（189–202 行）从事件流重算当前未决审批：WaitSuspended 加入 map、WaitResolved 移除。
- 所以刷新页面 / 断线重连 / 服务重启 / 跨机器，卡片都会重新出现。审批不是「推出去的消息」，是事件流里的事实。
- 反面：`pendingWait()` 在 `pending.size() > 1` 时直接抛 `IllegalStateException`——这是「多 PENDING」的死结入口，比唯一索引更硬。

**「先执行了再要审批」这个场景结构上不可能发生**，两道防线：
1. **顺序防线**：AgentRuntime 422–445，全部 `prepare()` 判定 → 全部只写 `DECIDED` journal → `if (approvalCalls 不为空)` 里 `eager.cancelAll()` 后立刻 `return WAITING`；`executeBatch` 在 482 行，**在 return 之后**。审批判定先于任何工具执行。
2. **效果防线**：需要审批的必然是 MUTATING，而 `EagerToolBatch.dispatch` 1729–1732 明确把 MUTATING 判为 `Disposition.INELIGIBLE`（注释：write call cannot leave the process before the decision journal and side-effect ledger are durable）。预执行只放行 READ_ONLY。

**部分批准（B 方案）真正要改的死点**：`resumePendingTools` 拿到混合状态时，已批的 entry 是 DECIDED（可执行）、未批的是 WAITING（需等），需要新增 `PARTIAL_WAIT` 语义；且 `commitResume` 只要见 PENDING 就返回 `WAIT_FOR_EXTERNAL`，整个 run 卡住。

**推荐绕法：用工具粒度换审批粒度**。让模型规划成 `execute_batch(items[])` 单个 tool_call，`proposedArguments` 带全部三项，用户在一张卡里逐项勾选；`WaitResolution.output` 本身是任意 JSON，可承载 `{approved:[0,2], rejected:[1]}`。审批点只有 1 个 → 绕开全部多 pending 问题；协议完全合法（一个 tool_call 对一个 tool_result）；部分选择语义落在工具内部，Runtime 无需感知。

## 追加：修正上一轮「数组方案」表述 + 会话崩溃后重建的真相

**⚠️ 撤回上一轮「推荐绕法」的表述**：`execute_batch(items[])` 方案只能**从源头避免**多 PENDING（前提是模型只发一个 tool_call），**不能解决「数据库里已经有 3 个 PENDING」**。数组只是客户端渲染形式，数据库里该 3 条还是 3 条，重挂起该卡还是卡。**数组 = 预防，不是治疗。**

**会话崩溃/重建后不会出现「两个审批结果」**：
- `waitId = UUID.nameUUIDFromBytes("wait:hitl:{sessionId}:{toolCallId}")`（AgentRuntime 786 行）—— 纯确定性推导，无随机无时间。
- 崩溃重启用同一 toolCallId 重算 → 同一 waitId → 数据库里**还是那一行 PENDING**，不存在第二条。
- 第二次点击是对同一行第二次 UPDATE，`WHERE status='PENDING'` rows=0 → 读回判 duplicate（同内容，`sameDecisionAs` 故意不含 resolvedAt）或 conflict（内容不同 / 已过 deadline）。
- 「先 DENIED 后 APPROVED」得到 CONFLICT，这是**正确行为**，已决议不可反悔。
- `WaitTimeoutProcessor` 的 TIMED_OUT resolutionId 也是确定性的（`wait-timeout:{waitId}:{deadlineAt}` 的 nameUUID），重复扫描只会得到 DUPLICATE，不重复提交。

**重建走的是纯 reducer 重放，不是新建审批**：`WaitSuspended` 事件在挂起那刻已写入事件流，`AgentSession.restore` 重放算出 pendingWait。审批从未消失。

**若真要支持「后端已有 N 个 PENDING」（路 A / 治疗）需改四处**：
1. 删 `one_pending_per_session_idx`
2. `AgentSession.pendingWait()` 由 `Optional` 改 `List`，删 198 行的 `pending.size() > 1` 异常
3. `resumePendingTools` 引入混合态（已批 DECIDED 可执行 / 未批 WAITING 需等）
4. `commitResume` 判定树区分「全决 → 恢复」与「部分 → 继续等」

**路 A 的残留死结（与部分批准同源）**：用户批 2/3 后第三个一直不批，deadline 到期自动 TIMED_OUT → journal 落 FAILED。此时前两个 ToolResult 要不要回填？回填则模型见「两成功一超时」可能重试；不回填则 assistant 消息 3 调用只有 2 结果，**协议非法**。根因仍是「协议要求 N 结果同时齐备，而它们在时间上分散到达」。

**路 B（预防，优先选）**：约束模型对需审批工具一次只调一个，并把 `MULTIPLE_TOOL_APPROVAL_UNSUPPORTED` 从硬失败改为「截断第一个 + 其余回填失败结果」让模型自重试。**能预防就别治疗——治疗要动不变量，不动不变量最便宜。**

## 追加：⚠️ 第二次撤回——多审批（客户端批量化）方案成立，前两轮结论作废

**用户提出的方案**：一次挂 3 个审批 → 客户端收齐 3 个结果后**发一个批量请求**（2 通过 1 拒绝）→ 没收到请求就默认全部超时。**这个方案成立，我前两轮的核心结论作废。**

**我错在哪**：我之前的隐含假设是「决议会分 N 次到达」，基于此推导「部分已批 → 无法回填 ToolResult → 协议非法」→ 死结。用户的方案里到达的永远是「全有」或「全无」，**没有中间态，死结不成立**。

**决定性证据：恢复路径已支持混合状态**。`resumePendingTools`（AgentRuntime 895–998 行）本来就是逐 entry 混合处理：
- `if (!entry.status().terminal())` → 进 pending → 执行
- 终态 → 直接用 `entry.observation()`
- **末尾无论终态非终态都 `run.messages.add(run.toolResultMessage(...))`**
所以「2 APPROVED(→DECIDED, 非终态, 执行) + 1 DENIED(→FAILED+TOOL_APPROVAL_DENIED, 终态, 用现成 observation)」完全跑得通，三条 ToolResult 补齐，协议合法。**不需要新增 PARTIAL_WAIT 语义——这是我上一轮的错误结论。**

**需改 6 处（都是局部，无结构性障碍）**：
1. `AgentRuntime` 425–430 `prepared.size() != 1` 硬失败 → 允许多个 approval call
2. `V14` 57 行 `one_pending_per_session_idx` 部分唯一索引 → 删
3. `AgentSession` 198 行 `pending.size() > 1` 抛异常 → 改返回 `List<WaitState>`
4. `AgentRunResult` 16 行 `waitState` 单个 → `waitStates` 列表（64 行构造器校验同步放宽）
5. `JdbcAgentRecoveryStore.suspendWait` 一个 checkpoint 挂 N 行，删 checkpointId 精确匹配校验
6. OpenAPI 加 `:resolveBatch`，body `[{waitId, outcome}]`

**resolveBatch 实现极省事**：内部串行调用现有 `resolveWait`，复用全部三层幂等（每个 wait 仍有自己的 deadline / duplicate 判定 / conflict 检测），全部成功后触发一次恢复。**对外一个批量请求，对内 N 个独立仲裁。**

**「拒绝的工具不给模型结果」的正确实现**：不是不给结果，而是给一个失败 ToolResult（DENIED→`TOOL_APPROVAL_DENIED`，超时→`WAIT_TIMEOUT`）。模型看到失败可以改路径重试，协议也合法。

**三个真实问题（非死结，但必须显式设计）**：
1. **批量请求原子性**：建议先全量校验、全通过再单事务写，避免「批了两条第三条冲突」的半截状态。
2. **超时与批量的交互（最易漏）**：`WaitTimeoutProcessor` 是有界扫描，同批三个可能只扫到两个 → 会出现「批了2个+第3个TIMED_OUT」歧义。**必须显式定义批次语义**。建议**共享 deadline**（客户端本来就是一个请求发三个，语义应绑定），避免部分超时。
3. **客户端「只批两个就关页面」**：按「没收到请求=全没批」规则，批了的白批。fail-safe 正确但产品上要提示（倒计时可见 / 离开将放弃提示）。

**必须锁死的不变量**：多 PENDING 之所以能跑通，靠的是「客户端批量化」约定。必须在 `suspendWait` 加显式约束——**一个 checkpoint 下的 N 个 wait 要么全被 resolveBatch 解决，要么全走超时，禁止混合**——用「批次共享 deadline」把这个假设变成可执行的不变量，防止将来有人绕开客户端调单个 `:resolve` 破坏前提。

**元教训**：前两轮我犯的错是「把一个可以通过产品/协议设计消除的前提（决议分次到达）当成不可变约束」。当死结的根源是「外部时序假设」而非「技术限制」时，先问「这个假设能被设计掉吗」。

## agent-runtime「为什么是分布式」讲解（只读分析，未改代码）

用户问：除了 Router 执行权 / fencing token / Redis 锁，还有哪些分布式体现。给出的四层拆解框架（可复用）：

1. **执行互斥**：`ExecutionAuthorityStore` 租约（30s TTL / 10s 续租）、单调递增 fencing token 覆盖「acquire → 终态提交」全区间、`commitIngress(request, fencingToken, now)` 把 token 传进持久层做拒绝。关键：Redis 锁只挡「别人进来」，fencing 才挡「自己晚到」。
2. **跨实例协同**：`CancellationSignalStore` 远程信号 + `CancellationToken.pollRemoteIfDue()` 有界轮询；用 `taskStartedAt` 过滤上一轮残留信号（分布式共享存储经典坑）；first-cause-wins；`PushEventRelay` Redis Lua 分配全局 seq + `sourceId` 防回环 + `Last-Event-ID` 重连。
3. **跨时间恢复**：`RecoveryPoint` 14 个固定崩溃注入点 + `ResumeAction`；Checkpoint/journal 分责；`WaitTimeoutProcessor` 只提交确定性 timeout，竞态交给 DB first-writer-wins 仲裁。
4. **跨系统/跨部署**：`SideEffectLedgerEntry` 账本（`UNKNOWN → RECONCILED`，禁止重放原写）、`CapabilitySnapshot` 版本冻结（恢复不静默套用新 Tool Schema）、Outbox 同事务。

**定位一句话**：不是「能跑在多台机器上的 Agent」，而是「把一次执行定义为跨进程、跨时间、跨外部系统的可判定状态机，任一节点可在任意时刻接管、继续、终止或收敛它」。

**诚实的边界（讲解时必须带上，别夸大）**：不提供通用分布式事务；线程中断只是协作式停止，不能撤销已发生的外部副作用；不为外部系统凭空制造幂等/查询能力；Push 是瞬态投影非审计流；Fork/子 Agent 未完成。

**架构上的关键卖点**：Core 零第三方主依赖（仅 Jackson），所有分布式能力都是 SPI 且默认 NOOP —— 同一套执行语义可换基础设施，单实例部署零成本、渐进启用。已发 Maven Central RC1。
