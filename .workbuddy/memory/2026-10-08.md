## Ark-Leto「Redis 大 Key」溯源（上下文压缩相关）

疑问：有说法称「压缩时把完整业务对象合进 session，最终引发 Redis 大 Key」——Redis 里不是放快照吗？

核实结论（文档出处）：
- 「大 Key」在文档中只有一处实质表述：§14.3 红线「`IndexedEntity` 的业务字段一律读 `displayFields`，不能依赖 `IndexedEntity.item`（item 已置 null 以治理大 Key）」，另见红线表 §2291。元凶是 **IdIndex 实体索引**，不是压缩摘要本身。
- Ark-Leto 的 Redis 快照不是薄指针，而是整个 session 投影的序列化（§5.3 `SnapshotStore.load → snapshot + EventStore.loadAfter(snapshot.position)`；§4.2② `restoreFresh` 从 Redis snapshot + 增量事件重建）。
- 业务对象进入 session 的链路：`ctx.registerEntity(entityType, naturalId, item)`（§14.3）→ order=250 `IdIndexInjectFeatureNode` 登记进 snapshot 并把真实 ID 改写成短 ID N1/U1（§14.2）→ `session.setLatestIdIndexSnapshot(...)` 写回 session 保证跨 dispatch 连续（§10 / §12）。
- 压缩与实体表是两条平行通道：压缩路径（§8.2 阶段 9/10 `PruneApplier.apply()` 物理删除、`filterCompactedMessages()`）只管 messages；`IdIndexSnapshotPruningCompactor` 是借 Compactor SPI 的副作用 hook、**不裁 messages**，且 `MIN_ENTITY_COUNT=50` 才触发（§14.3）。
- 动机与代价：短 ID ≈1 token vs 24 位 hex ≈12 token，为省 token + 免重复 RPC 必须保留实体表；实体表随 session 持久化 → 快照变胖。

## seekFlux 对照（结构上无同类风险）

- platform 生产代码零 Redis；session/recovery/compaction 全走 JDBC（`JdbcAgentSessionStore` / `JdbcAgentRecoveryStore` / `JdbcContextCompactionStore`）。
- Redis 只用于 agent-server 的 `ExecutionAuthorityStore`、`ShadowSettingsStore`，以及 online-server / worker-runner 的在线特征快照（`RedisOnlineFeatureRepository` / `OnlineFeatureSnapshotWriter` / `RedisUserInterestRepository`）。
- `runtime_checkpoints.payload` 只存 `{metadataPosition, statePosition, terminalPosition}` 引用集合，正文在 `workspace_events`；压缩摘要独立成 `agent.context_compactions` 表（`summary TEXT` + `UNIQUE(session_id, inclusive_cutoff, strategy_version)` 表达 no-gap）。同类风险在 PG 上表现为大行 / TOAST，而非 Redis 大 Key。

## 事件溯源的三层存储与「快照 vs 事件流」辨析

Ark-Leto 的分层（文档 §2.3 / §4.2② / §5.3）：
- L1 进程内 `sessionCache`：最快，靠 `isRemoteAhead(remotePos > cached.position())` 判定是否落后 → 落后就 evict 降级。
- L2 Redis：**事件流 Stream ＋ 快照 snapshot 都在 Redis 内**，是热层与跨 pod 强一致读点，带 TTL（冷会话自动下沉）。
- L3 DB：全量事件 ＋ 快照，冷备；仅在 Redis 缺失时走链路 4 冷恢复，**恢复后回写 Redis snapshot**。
- 恢复四条链路优先级：① 本地缓存 → ② snapshot + `loadAfter(position)` 增量 → ③ `loadAll` 全量重放 → ④ DB 冷恢复。
- `SnapshotPolicy` 三触发：`saveOnSuspend` / `saveOnComplete` / `saveIntervalEvents(每 N 次 append)`。

关键辨析（回答「事件都持久化了，为什么还要快照」）：
- **持久化解决「不丢」，快照解决「重建快」。两者正交。**
- 快照必须自足（含快照点之前的完整状态），否则截断不成立 —— 这正是"完整投影"而非"指针"的原因。截断收益：O(N) → O(1)+O(M)。
- 判据：**删掉全部快照系统仍正确**（退回链路 3 全量重放）；**删掉事件流数据就真没了**。所以不是存两份，是一份真相 + 一个可丢弃的物化视图。
- 与 `RuntimeCheckpoint`（进度指针，回答"从哪继续"）区分：指针不影响恢复成本，基线才影响。

seekFlux 同构佐证（用户已澄清本轮问 Ark-Leto，此条仅作旁证）：
- `V16__agent_reference_snapshots.sql` 建 `agent.session_snapshots(session_id, event_position, schema_version, payload JSONB, PRIMARY KEY(session_id, event_position))`，其 COMMENT 原文：`State baseline and pending event references. Original event/message bodies remain append-only in workspace_events.`
- `JdbcAgentSessionStore.restoreFresh` = 快照基线 + `views`(受 `compressedThrough` 与 `retainedEventPositions` 过滤) + `tail`；`saveSnapshotIfNeeded` 用 `${seekflux.agent.session.snapshot-interval-events:100}` 稀疏触发，`FOR UPDATE` 取 head，`snapshot.position() != head` 抛 `Session snapshot high-water mismatch`，写入 `ON CONFLICT DO NOTHING`。
