## agent-runtime 请求全链路状态流转梳理（面试准备）

围绕「一个请求进来 → 返回结果」的完整数据流，把 agent-runtime 拆成 **7 段**（非 2 段），逐段标注状态读写点：

- ① 准入纯读短路（pendingWait / QUEUE 模式校验，`DefaultRouter.execute`）
- ② 抢执行权 `tryAcquireExecution`（唯一竞争型写：Redis 租约）
- ③ `sessions.commitIngress` 写 USER_MESSAGE 事件（position+1，IDLE→EXECUTING）
- ④ `restoreFresh` 把事件流重放成 AgentSession 投影
- ⑤ `recoveryStore.commitResume(ResumeIngress)` 产出 RecoveryPlan（7 动作，4 种进循环）
- ⑥ 水位校验 + FAIL_UNSAFE fail-closed（`SessionExecutor.executeSegment:367-383`）
- ⑦ 循环 → 终态 → drain（复用同一 authority）

### 核心结论（可复述）
- **AgentSession 是事件溯源投影，不是被直接写的状态**：`AgentSession.restore()` 的 switch 是 reducer。13 类 WorkspaceEvent 里只有 7 类推动 status（SessionCreated/UserMessage/WaitSuspended/WaitResolved/RunCompleted/RunCancelled/RunFailed），另 6 类只是事实记录。
- **五层状态载体，时间尺度不同**：内存 RunState（单次 run）/ 执行租约（秒级，唯一会自动消失的状态）/ 轮级快照 RuntimeCheckpoint（每轮覆盖）/ 工具日志+副作用账本（一次性事实，不可重建）/ 会话事件流（永久只追加，唯一事实来源）。
- **一轮 turn 固定 5 次写入**：savePreTurn → recordToolDecision → markToolExecuting(±prepareSideEffect) → recordToolResult(±recordSideEffectResult) → savePostTurn。
- **所有判定都不改变流程形状**：RecoveryAction 的差异只落在 4 个初值上（startStep / observations / remainingBudgetMillis / snapshot.definition）。判定逻辑收敛一处，执行动作集合封闭。
- 类名与职责对应：准入=DefaultRouter，段执行=SessionExecutor，循环=AgentRuntime，轮内组装=DefaultAgentLoop + ContextEngine。

## 快照的存储形态 与 UNKNOWN 语义（补）

- **快照表很薄，存指针**：`JdbcAgentRecoveryStore.persistCheckpointFacts()` 把一次快照拆成 4 类 append-only 事实写进 `workspace_events`（message / EXECUTION_METADATA / EXECUTION_STEP / EXECUTION_TERMINAL / EXECUTION_PROGRESS），`runtime_checkpoints.payload` 只存 `{metadataPosition, statePosition, [terminalPosition]}`。消息正文不重复存。
- `messageCutoff` = `EXECUTION_PROGRESS` 事实的 position，与 `session.position()` 同一张表，所以能做水位校验。
- `checkpointId` 确定性 UUID + `ON CONFLICT (session_id, request_id) DO UPDATE` → 一条 request 只有一行快照，滚动覆盖。
- **UNKNOWN 的主来源是 `commitResume` 开头的两条 UPDATE**（`JdbcAgentRecoveryStore:76-104`）：开新尝试前把上次残留的 `EXECUTING` 行（journal + ledger 两表）改成 `UNKNOWN`，同时把 `fencing_token` 换成新的（夺回写入权）。副来源是运行时的 `markSideEffectsUnknown`（工具抛异常 / `abandonPending`），只动 ledger。
- **UNKNOWN 只在恢复路径判定**（`planRecovery` / `recoverMutatingSideEffect`），不是每轮、也不是每个工具前。
- 精妙点：状态机"可再推进集合"由 SQL WHERE 白名单编码——`markToolExecuting` 允许 `IN ('DECIDED','UNKNOWN')`，`recordToolResult` 允许 `IN ('DECIDED','EXECUTING','UNKNOWN','WAITING')`，终态不在任何白名单里 → 写入即冻结。`messageStatus` 把 UNKNOWN 映射为 `WAITING` 喂给模型。
- 语义分界：`EXECUTING` = 本次尝试内；`UNKNOWN` = 跨尝试。"我不知道"必须与"它失败了"分开，因为对 MUTATING 工具的恢复策略完全相反。

## 「seekFlux 能否直接加沙箱机制」可行性评估

- **事实**：全仓 `.java/.py/.sh` 对 `sandbox|沙箱|ProcessBuilder|docker` 零匹配 → 确认无任何沙箱机制。原因是当前工具形态不需要：只有 `search_direct` / `search_filtered` 两个 `READ_ONLY` 进程内适配器（直连 Search UseCase），加远端 MCP（信任边界见 ADR-014），`SkillDefinition` 只是 prompt 文本（instruction ≤16KB，不执行代码）。没有 code-exec 类工具。
- **对照 Ark-Leto**：沙箱不是主链路机制，挂在 Tool 层——`ToolDefinition.runtime: ToolRuntime(LOCAL/SANDBOX)`、`@ToolDef(sandbox=false)`、`SandboxAwareTool`、`SandboxRuntime.acquire()/release()`（404 → evictAndReacquire 重试一次）、`SandboxBashTool/Python/Node/TS`、`SandboxUnavailableException → failSession("SANDBOX_UNAVAILABLE")`。说明沙箱是**外部沙箱服务**，只服务代码执行类工具。
- **结论**：架构接缝很干净（唯一收口点 = `AgentTool.execute(AgentToolContext)`，全仓唯一调用点 = `DefaultAgentToolExecutor.execute()`），可用 `SandboxedAgentTool implements AgentTool` 装饰器 + 新 `SandboxRuntimePort(SPI)` 零侵入接入；但**不能"直接做"**——缺的是沙箱承载物与"被沙箱的工具"，不是接缝。
- **关键约束**：`platform/agent-runtime` Core 已发布 RC1（Maven Central，零第三方主依赖 + `jdeps` 字节码边界校验，ADR-015）→ 沙箱 SDK 不能进 Core，实现必须放独立模块，Core 只留 SPI。
- **待补前提**：P0 沙箱承载物（远程服务/子进程/容器，属部署形态，最大工程量）、确定谁进沙箱、CancellationToken + remaining deadline 传到沙箱进程、资源硬限额与 kill、网络/FS/凭据隔离；P1 接 AR-4 副作用账本语义（沙箱调用=外部调用，UNKNOWN 不重放）、CapabilitySnapshot 冻结沙箱版本、低基数观测；P2 沙箱池化 acquire/release 生命周期。
- **定位**：应作为新 AR 阶段立项（类比 AR-9C「后置可选 + 需真实用例」），非一行开关。评估：接缝可行度 9/10，沙箱本体从零 3/10，整体"现在直接做完整版" 4/10，草率落地的安全假象风险 7/10。
