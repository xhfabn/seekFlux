我认为它最有价值的评测思路是：**把一个 Agent 能力拆成几个可观察的阶段，用真实实现处理受控数据，保存中间证据，再用独立规则判断结果；如果要验证改进是否有效，就在相同条件下做 A/B 对照。**

其中，**记忆整理 A/B 实验**最值得深入理解。它比“给 Agent 一批问题，最后算准确率”更进一步：不仅检查任务有没有完成，还检查完成过程中有没有丢信息、重复信息或破坏关联。

下面以这个实验为主线，把设计、执行、验证和定位连起来讲。

### 1. 它首先明确：到底要验证什么能力？

假设 Agent 已经积累了一些用户记忆：

```text
用户资料.md
├── 用户是后端开发者
├── 用户喜欢简洁回答
├── 用户使用 Java
└── 用户不喜欢回答中包含太多表情

偏好.md
├── 用户喜欢简洁回答
└── 用户习惯先看结论
```

随着使用时间变长，可能出现：

- 同一个事实重复保存在多个文件。
- 偏好混进基本资料。
- 文件越来越大，应该拆分。
- 同类记忆散落在不同目录，需要合并。
- 合并后，原文件的引用需要指向新文件。

它要验证的是：**模型能不能合理整理这些记忆，并且保持信息完整。**

这里其实有两个独立问题：

| 问题 | 示例 |
|---|---|
| 整理动作是否正确？ | 应该拆分的文件有没有拆分，偏好有没有进入偏好类型 |
| 信息是否完整？ | 整理后有没有丢失、重复或篡改原来的事实 |

这一步很重要。

如果只检查“最终是不是两个文件”，模型把一半内容删除，也可能通过。

所以它不会只看一个最终现象，而是把“任务完成”和“信息完整”分别验证。

### 2. 怎么把这个能力做成可评测的案例？

每个案例都需要三部分：

```text
初始状态
    已存在的记忆文件、文件内容、类型和位置

Agent 可见输入
    对话信息，以及通过读取获得的已有记忆

裁判专用期望
    应当保留的事实、允许的组织结构、应当建立的替换关系
```

注意：**第三部分不能直接交给被评测的模型。**

例如，一个案例可以预置：

```text
初始文件：
profile.md

内容：
F01：用户是后端开发者
F02：用户使用 Java
F03：用户喜欢简洁回答
F04：用户习惯先看结论
```

评测方知道：

- F01、F02 属于基本资料。
- F03、F04 属于偏好。
- 整理后四个事实都应保留。
- 不应该产生两个相同的 F03。

但模型看到的是生产指令、对话和文件内容，并不直接得到“把 F03、F04 搬到某个指定文件”的标准答案。

这样测到的才包含自主判断能力。

它另外也有更明确指导的确定性整理案例。两类实验回答的问题不同：

- 明确告诉模型怎么整理：检查执行能力。
- 只提供真实输入和生产规则：检查自主整理能力。

**会按给定步骤执行，不代表会自己判断步骤。**

这点对应到我们这里，就是 scripted planner 测试通过，不等于真实模型已经具备正确规划能力。

### 3. 它怎样确保测的是实际系统，而不是另写的演示程序？

这是一个很有价值的做法：**复用生产实现，只替换实验需要控制的输入。**

它的 `AutonomousProvider` 继承生产的 `SessionExtractContextProvider`，保留生产指令路径和会话包装，主要控制：

- 初始有哪些记忆文件。
- 预取时返回哪些内容。
- 模型读取文件时获得什么结果。

可以理解为：

```text
生产指令与处理路径
          +
受控的初始文件和读取结果
          ↓
模型实际完成整理任务
```

这样做有两个好处。

第一，实验更接近实际使用。否则你为评测单独写了一套更详细的提示词，测出的可能只是“评测提示词很好用”。

第二，输入可控。每次都从同样的文件和事实开始，才方便比较不同方案。

但也要理解它的边界：这种方式控制了已有文件和读取结果，**不等于覆盖了整个真实存储、检索和服务部署链路**。它主要隔离验证记忆整理机制。

### 4. A/B 对照具体改变什么？

这组实验会比较不同输出协议，例如 JSON 与受限 Python。

可以把它理解为：

> 模型要表达同一组整理操作，使用不同的表达和执行协议，会不会影响成功率、信息完整性和成本？

它尽量保持以下条件一致：

| 固定条件 | 为什么固定 |
|---|---|
| 模型 | 避免把模型能力差异归因于协议 |
| 初始文件 | 避免两边面对不同难度 |
| 生产指令与 schema | 避免一边得到更多指导 |
| 重试预算 | 避免一边有更多纠错机会 |
| 输出 token 上限 | 避免一边拥有更多表达空间 |
| 案例与重复轮次 | 让结果可以逐项配对 |

然后主要改变要研究的协议。

```text
同一案例、同一初始状态
         ├── 方案 A：JSON 协议
         └── 方案 B：受限 Python 协议
```

这就是它评测思路中的关键：**实验要能解释变化来自哪里。**

如果同时换了模型、提示词、数据、重试次数和协议，最后即便提高了 10%，也不知道是哪项改动起作用。

### 5. 跑完后，它具体检查什么？

不是只让另一个大模型回答“整理得好不好”。

这里有大量可以直接验证的条件。

**第一类：事实是否保住了。**

对于已知事实集合，检查：

```text
原来有的事实，现在还在吗？
同一事实是否出现在多个位置？
事实内容有没有改变？
是否出现预期以外的标记事实？
```

确定性案例使用事实标识辅助检查；自主实验也包含基于规范化文本的事实定位。

例如：

```text
F01：保留一次
F02：保留一次
F03：保留两次
F04：不存在
```

那么即使文件结构很漂亮，也能明确识别：

- F03 重复。
- F04 丢失。
- 信息完整性不通过。

**第二类：事实放得对不对。**

例如偏好有没有进入偏好类型，资料有没有留在资料类型。

这能区分两种错误：

```text
事实还在，但是放错地方。
事实已经不在了。
```

它们的修复方向不同，不能都归为一个笼统的“整理失败”。

**第三类：结构和关系是否正确。**

根据案例检查：

- 是否完成合并。
- 是否完成拆分。
- 路径是否规范化。
- 原文件是否按要求退出。
- 替换关系是否指向正确目标。

有些自主拆分指标允许“至少两个文件”，而不是强制某两个文件名。这说明它在部分地方验证的是业务意图，而不是机械要求模型生成唯一答案。

不过，这些检查仍然有适用范围：**已知事实的出现次数检查，不是对任意自然语言内容的完整真实性证明。**

### 6. 它怎么判断哪个方案更好？

除了汇总成功率，它还比较每个配对案例的胜负：

| A 的结果 | B 的结果 | 含义 |
|---|---|---|
| 成功 | 成功 | 两者都能处理 |
| 失败 | 失败 | 共同薄弱点 |
| 成功 | 失败 | B 引入退化 |
| 失败 | 成功 | B 带来改善 |

这比只看两个总分有价值。

假设：

```text
A：通过 8 个案例
B：通过 8 个案例
```

总分相同，可能有两种完全不同的情况：

```text
情况一：双方通过的是同样的 8 个。
情况二：B 修好了 2 个，同时又弄坏了另外 2 个。
```

第二种情况下，“平均分没变”掩盖了明显的能力变化。

它还提供双侧精确 McNemar 检验，用于观察配对二元结果的差异。但不能因此把少量案例上的重复运行理解成大规模场景验证，仍需看案例覆盖和随机波动。

### 7. 出现问题后，怎么定位？

这组实验最有价值的地方，是不同失败能够对应不同证据。

以下是基于它保存的结果与分项指标可以进行的分析，**不是说项目已经自动完成全部根因诊断**：

| 观测结果 | 优先排查方向 |
|---|---|
| 输出无法解析，整理无法应用 | 输出协议、格式约束、解析和重试机制 |
| 操作执行了，但文件没有按预期拆分 | 模型对整理目标的判断、生产指令 |
| 文件拆分了，但事实丢失 | 模型输出内容、操作应用过程 |
| 事实存在但重复 | 合并去重、旧文件处理 |
| 事实完整但类型放错 | 分类判断、schema 理解 |
| 内容正确但替换关系错误 | 引用迁移或替换逻辑 |
| A 正常、B 在同一案例失败 | 优先检查两方案实际改变的部分 |

例如，“拆分成功但丢了 F04”可以继续沿着证据看：

```text
初始文件里是否确实存在 F04？
          ↓
模型实际读取的内容中是否包含 F04？
          ↓
模型生成的整理操作中是否包含 F04？
          ↓
应用操作后的文件中是否包含 F04？
```

对应四个不同层次：

- 初始数据问题。
- 输入或读取问题。
- 模型整理问题。
- 操作执行问题。

**定位能力来自保存了各阶段的输入和输出，不是来自最后那一个分数。**

### 8. 如果要看完整 Agent 链路，它又怎么做？

上面是机制级实验。它的 LoCoMo 记忆问答评测，则把范围扩大到完整记忆链路：

```text
历史对话
    ↓
按身份、时间写入 Session
    ↓
提交 Session
    ↓
等待记忆处理任务完成
    ↓
在对应身份下发起新的问题
    ↓
Agent 检索并使用记忆
    ↓
保存答案、工具使用情况和日志
    ↓
独立 Judge 判分
    ↓
按题型汇总质量与成本
```

这里有三个特别值得借鉴的处理。

**一是导入必须经过真正要评测的能力。**

想评记忆形成，就要经过 Session 提交和记忆处理。直接把原始聊天记录塞进资源库，测到的主要是原文检索，不能证明记忆提取有效。

**二是必须等待准备阶段完成。**

提交返回 `accepted`，不等于记忆已经可用。导入器拿到任务 ID 后会轮询任务状态，避免刚提交就开始提问。

**三是执行和评分分离。**

先保存模型答案与运行证据，再让 Judge 评分。以后修改裁判标准，可以基于同一批回答重新评，不必重新花成本跑 Agent。

完整链路答错时，可以按照下面的顺序排查：

| 阶段 | 要问的问题 |
|---|---|
| 原始数据 | 历史里真的有这个信息吗？ |
| 记忆生成 | 信息是否被提取并正确更新？ |
| 作用域 | 是否用正确的用户和记忆范围查询？ |
| 检索 | 相关记忆有没有被召回？ |
| 上下文组装 | 召回内容是否真正进入模型输入？ |
| 回答 | 模型是否正确使用了这些信息？ |
| 判分 | 裁判是否正确理解答案和标准？ |

这些证据分布在原始数据、记忆存储、运行 CSV 和日志中，并不是一个答案 CSV 就足以完成全部定位。

还要注意它的实现局限：部分 LoCoMo 脚本会把 Judge API 失败写成 WRONG，部分执行错误使用零耗时或零 token。因此我们借鉴流程时，应把**执行错误、模型答错、裁判错误、未测量指标**明确分开。

### 9. 对我们最直接的价值是什么？

它说明，一个有价值的通用评测模块应该帮助使用者回答四个问题：

1. **这次到底测了什么？**
   是工具执行、模型规划、记忆整理，还是完整业务任务？

2. **结果为什么可信？**
   初始状态受控、期望没有泄漏、生产实现被实际调用、判定规则明确。

3. **改动真的带来改善了吗？**
   相同案例成对比较，保留逐题退化和改善，同时观察成本。

4. **失败发生在哪个阶段？**
   有输入、工具调用、状态变化、最终输出和评分依据，可以逐层检查。

所以，对我们来说，最值得吸收的不是再增加几个数据集，而是让使用者只需要提供**场景初始状态、真实能力适配和业务成功条件**，模块就能统一完成执行、采证、故障控制、评分与对照。这样它才真正降低了写评测和查问题的成本。
