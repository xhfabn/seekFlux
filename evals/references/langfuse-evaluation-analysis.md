# Langfuse 怎样执行 Agent 评测并定位问题

Langfuse 最有价值的评测过程，是把 **真实运行轨迹 → 自动评分 → 人工复核 → 回归数据集 → 新旧版本对照** 连起来。分数不再孤立地存在，而是
能追到被测 Agent 做了什么、裁判看到了什么，以及这个案例最初来自哪里。

它的主定位是 LLM 工程平台，提供观测、评测、数据集和实验管理。接入方仍需要提供自己的 Agent、工具、业务环境与正确性标准。下面用一个“修改订单地址”
的例子讲清流程；该订单案例用于解释机制，并非 Langfuse 内置数据集。

本文基于本地 `D:\workSpace\langfuse`，提交 `074731ce5c321efa1f3a1e42ede780010b49e1cd`。本次阅读了相关实现与测试源码，没有部署服
务或执行测试。跨仓库源码链接适用于 Langfuse 与 SeekFlux 位于同一父目录的布局。

### 1. 先明确它要解决什么问题

假设你的 Agent 回答：

> 已经帮你修改了收货地址。

单看这句话，我们不知道：

- 是否真的调用了更新工具。
- 是否修改了正确的订单。
- 是否拿到必要的用户确认。
- 工具执行是否成功。
- 数据库最终状态是否正确。
- 评分器为什么给出高分或低分。

Langfuse 的做法是先记录运行过程，再把评分挂回这个过程。因此，“答案质量”“工具执行情况”“运行成本”“裁判是否正常”可以分开分析。

但它不会自动知道订单系统的真相。如果应用只上传最后一句话，没有上传工具参数、结果或业务状态，那么平台也只能基于有限证据判断。

**它提供证据组织和评分执行能力，业务正确性仍然需要明确的判定依据。**

### 2. 用几个对象把整个过程串起来

| 对象 | 可以怎样理解 | 在例子中的含义 |
| --- | --- | --- |
| Trace | 一次被观测的执行过程 | 这次修改地址请求 |
| Observation | 执行过程中的一个步骤或观测对象 | 模型规划、查询订单、更新地址 |
| Dataset item | 一条可以重复使用的案例 | 用户请求、期望状态、案例元数据 |
| Experiment / run | 某个方案在一批案例上的运行 | Agent v1 或 v2 的一次实验 |
| Evaluator | 怎么评分 | 地址是否正确、回答是否忠实于工具结果 |
| Rule / assignment | 何时评谁、使用哪个裁判 | 对某类运行抽样，绑定正确性和完整性裁判 |
| Score | 一项评分及关联信息 | 正确性 0、附上原因、关联原始运行 |
| Evaluation execution | 裁判自身的一次执行 | 裁判收到什么、用了哪个模型、有没有报错 |

其中最重要的分离是：**被测 Agent 的执行，与裁判自己的执行，是两件事。**

业务执行成功，裁判可能超时；裁判执行成功，也可能给业务结果打零分。不能用一个“成功/失败”字段同时表示它们。

### 3. 两种入口：在线评测和离线实验

它有两种常用使用方式，后面的评分机制可以复用。

```text
在线入口：
真实业务运行 → 上报轨迹 → 规则过滤和采样 → 评分

离线入口：
固定数据集 → 运行待测方案 → 关联案例和轨迹 → 评分

共同后续：
查看评分 → 打开原始执行和裁判执行 → 复核 → 修正 → 再实验
```

在线评测用于发现真实使用中的问题，离线实验用于在受控案例上验证改动。线上样本进入回归集后，两者就能形成持续迭代过程。

这个过程需要使用者组织，并不是平台会自动判断所有坏案例、生成正确答案并完成修复。

### 4. 在线评测第一步：先把实际过程记录下来

应用通过观测接入上报 trace/span，Langfuse 的 ingestion 将其标准化为 observation。

例如，应用可以记录：

```text
修改地址请求
├── 模型规划
│   ├── 输入：用户要求
│   └── 输出：先查询订单
├── 查询订单
│   ├── 参数：orderId
│   └── 结果：订单与当前地址
├── 更新地址
│   ├── 参数：orderId、newAddress
│   └── 结果：执行回执
└── 最终回答
```

这里有哪些内容，取决于应用如何埋点、是否使用相应集成以及是否上报字段。平台不是自动旁观所有外部系统的工具。

对于订单最终状态，接入方还可以采集独立查询结果，交给确定性检查器判断。它比仅用 Agent 自己的回答作为证据更可靠。

源码入口：[OTel 处理](../../../langfuse/worker/src/features/otel-ingestion/processOtelEvents.ts)。

### 5. 第二步：规则决定哪些数据需要评分

不是每条 observation 到达就无条件调用裁判。

规则先回答几个问题：

- 是否属于当前项目和允许的环境？
- 是否匹配对象名称、类型等过滤条件？
- 当前规则与裁判是否仍然可执行？
- 是否被采样选中？
- 这一条数据要交给哪些裁判？

规则与裁判分离后，同一个正确性裁判可以服务多个场景；同一个场景也可以同时运行正确性、格式和忠实性等多个裁判。

#### 为什么它使用确定性采样？

假设只评测 10% 的运行。如果每次重试都重新随机抽样，同一个对象可能第一次不评，第二次又变成要评。

当前 observation 路径对目标 span ID 进行带固定域标识的 SHA-256 计算，映射到 0 到 1 之间，再与采样率比较。

```text
目标 ID → 稳定采样值 → 是否小于采样比例
```

因此同一目标的采样决定稳定，10% 的样本集合也可以包含在 20% 的集合中。这有助于控制成本和减少重试带来的样本变化，但不等于自动保证实验统计有效或新旧版本严格配对。

#### 为什么裁判自己的轨迹不能再被普通规则选中？

因为裁判也会产生观测。如果不排除，就可能出现：

```text
业务运行 → 裁判运行 → 评裁判的裁判 → 继续产生裁判
```

调度与执行会检查内部评测环境，避免这样的递归。Prompt 实验根 observation 有特定处理，不代表其所有子步骤都应被无差别评分。

源码：[调度器](../../../langfuse/worker/src/features/evaluation/observationEval/scheduleObservationEvals.ts)、[确定性采样](../../../langfuse/worker/src/features/evaluation/deterministicSampling.ts)。

### 6. 第三步：保存评分输入，异步创建任务

同一个 observation 命中多个评分配置时，调度器把观测数据上传到对象存储，供多个裁判任务读取，而不是每个裁判都重新去业务系统查询一遍。

这让多个裁判能够基于同一份已捕获证据评分，也避免把裁判调用放在业务请求的同步关键路径上。

随后按规则与 evaluator assignment 创建任务，通过 BullMQ 交给 worker 执行。任务身份包含规则、assignment、trace、span 等信息；部分批次还包含执行作用域，便于区分重试和新的批次执行。

这里有两个边界：

1. 保存的是评分所需的观测数据，不是完整业务数据库或 Agent 状态快照。
2. 稳定任务和分数 ID 有助于处理重复投递，但不能保证裁判模型永远只调用一次。例如裁判返回后分数写入失败，重试仍可能产生额外调用成本。

当前代码还保留 trace/dataset 的其他调度路径，支持自己的延时等规则。不能把 observation 的处理时序概括成所有评测路径的唯一实现。

源码：[在线调度](../../../langfuse/worker/src/features/evaluation/observationEval/scheduleObservationEvals.ts)、[队列处理](../../../langfuse/worker/src/queues/evalQueue.ts)。

### 7. 第四步：把证据映射成裁判真正收到的输入

到了 worker，首先再次检查规则是否停用、assignment 是否存在、裁判是否被禁用，然后读取已保存的证据。

下一步不是直接把整条 trace 原样扔给模型，而是按变量映射提取评分需要的内容。例如：

```text
question        ← 用户输入
actual_answer   ← 最终回答
tool_result     ← 更新地址工具结果
expected_output ← 数据集中的期望结果（离线实验时）
```

上面是解释用映射，不是要求所有裁判必须使用这些变量名。

LLM 裁判需要用户配置变量映射。代码裁判有服务端准备的数据映射，再由用户代码选择和处理具体内容。

**实际映射后的输入一定要能检查。** 原始 trace 有正确内容，不代表裁判真的收到正确字段。当前 observation 提取逻辑中，缺失字段可能返回空值，
部分 JSON selector 异常会回退原值，所以错误映射未必都会立刻变成显式失败。

如果发现一个很合理的回答得到低分，应先检查裁判输入，再讨论“裁判模型是不是不够聪明”。

源码：[变量提取](../../../langfuse/packages/shared/src/server/evals/extractObservationVariables.ts)、[worker 执行入口](../../../langfuse/worker/src/features/evaluation/observationEval/observationEvalProcessor.ts)。

### 8. 第五步：按问题选择评分方式

#### 能确定性判断的，用代码或外部规则

例如：

- 返回 JSON 是否符合约定。
- 最终地址是否等于期望地址。
- 订单 ID 是否一致。
- 是否出现规定之外的状态变化。

Langfuse 支持 Code evaluator，也支持通过 API/SDK 上报自定义评分。代码执行器需要相应 runner/dispatcher 配置，并非所有部署天然已经具备运行用户代码的环境。

业务数据库查询、隔离环境初始化与副作用采证，应由接入方安排。平台不自带“订单修改成功”的业务定义。

#### 需要语义判断的，用 LLM Judge

例如：

- 最终说明是否忠实于工具结果。
- 是否遗漏用户要求。
- 回答是否与参考答案语义一致。

执行器会验证输出定义、解析模型配置、根据变量编译裁判提示词，请求结构化输出，再验证并规范化分数。

结构化输出解决的是“结果能否按协议使用”，不是“裁判意见必然正确”。评分标准、示例、模型和人工校准仍然决定它的有效性。

#### 有争议的，用人工标注

人工复核可以给 trace/session 打分、写评论，并通过标注队列分配和处理样本。它适合判断：

- Agent 真错了，还是裁判误判？
- 标准答案是不是写错了？
- 这个问题是否存在多种合理答案？
- 现有 rubric 是否需要调整？

源码：[LLM 评分服务](../../../langfuse/worker/src/features/evaluation/evalService.ts)、[代码评分](../../../langfuse/worker/src/features/evaluation/codeBased/executeCodeBasedEvaluation.ts)、[人工标注队列](../../../langfuse/web/src/features/annotation-queues/README.md)。

### 9. 第六步：给分数建立双向证据关联

它不只保存“正确性 = 0.2”，还保存分数对应的业务 trace/observation、裁判和规则身份、评论以及裁判执行 trace ID。

```text
                 一项 Score
                 /       \
                /         \
       被测 Agent 运行     裁判自身运行
       实际做了什么         为什么这样打分
```

裁判 trace 可以包含提示词编译、模型调用、输出验证等阶段，以及实际输入输出和错误。

这使两类问题可以分开排查：

- 分数低：检查业务运行证据和评分理由。
- 无分数或评分异常：检查裁判执行证据、变量、配置和服务错误。

共同完成逻辑会要求非空分数列表，上传并把分数加入 ingestion 队列，然后把执行标为 COMPLETED。因为分数写入查询系统仍有异步过程，COMPLETED 不保证界面立刻可见。

源码：[分数关联](../../../langfuse/worker/src/features/evaluation/evalScoreEvent.ts)、[完成处理](../../../langfuse/worker/src/features/evaluation/evalCompletion.ts)。

### 10. 它怎样区分答错和评测系统故障？

这是比“捕获所有异常然后记零分”更有价值的设计。

| 情况 | 应怎样解释 | 源码中的处理方向 |
| --- | --- | --- |
| 裁判正常给出低分 | 被测结果在该标准下质量较低 | 保存有效 Score |
| 下载评分输入失败 | 评测基础设施故障 | 可重试 |
| 保存的输入 JSON/schema 无效 | 评分输入不可用 | 不可恢复错误 |
| 模型配置无效 | 裁判配置错误 | 不可恢复，部分情况会禁用裁判 |
| 裁判输出格式无效 | 评分协议失败 | 不可恢复错误 |
| 分数保存失败 | 评分结果写入故障 | 可重试 |
| Provider 暂时不可用或限流 | 执行尚未完成 | 符合条件时延后或重试 |

队列逻辑会在永久错误或尝试耗尽时记录 ERROR，避免第一次临时失败就写终态，导致后续重试被跳过。

但不能据此宣称每个计划案例都有最终分数。部分找不到 observation 的路径会在重试耗尽后记录警告而不创建评测。最终仍要检查评分覆盖率和未评分样本。

源码：[错误分类](../../../langfuse/worker/src/features/evaluation/evalFailureErrors.ts)、[队列执行](../../../langfuse/worker/src/queues/evalQueue.ts)。

### 11. 离线实验具体怎么实施？

#### 第一步：建立版本化的数据集

Dataset item 可以保存 input、expectedOutput、metadata、ACTIVE/ARCHIVED 状态，并关联来源 trace/observation。

更新案例时，仓库通过 validFrom/validTo 表达版本区间，支持按时间版本查询。修改标准答案以后，历史实验仍可以关联到对应案例版本。

例如：

```text
案例：
用户请求：把订单 A 的地址改为地址 B
期望结果：订单 A 的地址为 B，其他字段保持不变
元数据：需要用户确认、订单可修改
来源：某条线上失败 trace
```

期望结果由领域方定义。自动从线上错误回答复制出的文本，不能直接当正确答案。

#### 第二步：明确是谁运行被测程序

这里必须区分两种实施方式。

| 方式 | 谁执行 | 适用范围 |
| --- | --- | --- |
| 平台托管 Prompt 实验 | Langfuse worker 编译 prompt 并调用模型 | 提示词、模型、结构化输出等对照 |
| 自定义 Agent 实验 | 你的外部执行器运行 Agent，再上报轨迹和实验关联 | 多轮规划、工具执行、业务环境、状态恢复 |

当前托管实验主路径调用 `generateLLMText`，即使提供工具定义，也不能把它理解成自动托管你的完整业务工具循环。

UI 的 remote experiment 功能可以向配置的外部地址发 POST 触发请求。HTTP 请求成功，仅代表触发被接受，不代表外部 Agent 跑完、轨迹已上传或评分已完成。

对于我们的 Java Runtime，比较自然的接法是由已有评测执行器准备案例、运行真实 Agent、采集证据，再与 Langfuse 的实验和评分体系关联。具体适配需要另外实现。

#### 第三步：执行并关联案例、版本和轨迹

托管路径会查询指定版本的 ACTIVE items，校验输入是否满足 prompt 变量要求，跳过已有 run item 的案例，为新案例建立运行记录和稳定 trace 身份。

正常执行使用 input 替换 prompt 变量，expectedOutput 进入实验上下文供后续评分。这个分离减少直接答案泄漏，但使用者仍可能把答案混进 input，平台不能替用户保证数据完全干净。

#### 第四步：评分，然后逐项比较

实验比较可以围绕案例查看不同实验的输出、trace、耗时、成本和分数，并区分 observation 级与 trace 级评分。

应该优先看：

```text
同一个案例：
旧方案输入 → 旧方案轨迹 → 输出与分数
新方案输入 → 新方案轨迹 → 输出与分数
```

这样能找到“总体均分提高，但某类任务退化”的具体案例，而不是只看一个平均值。

源码：[数据集契约](../../../langfuse/fern/apis/server/definition/dataset-items.yml)、[版本实现](../../../langfuse/packages/shared/src/server/repositories/dataset-items.ts)、[托管实验](../../../langfuse/worker/src/features/experiments/experimentServiceClickhouse.ts)、[远程触发](../../../langfuse/web/src/features/datasets/server/remoteExperimentHelpers.ts)、[实验比较](../../../langfuse/web/src/features/experiments/server/router.ts)。

### 12. 实验完成时，不能只看一个 success

源码中一个特别需要理解的边界是：托管实验逐项执行，部分错误被记录后继续，整个作业最后仍可能返回 success；模型调用失败与评分异步调度失败也有分别处理的路径。

所以以下四件事必须分开：

```text
队列作业处理结束
        ≠
每个模型调用都成功
        ≠
每个案例都完成评分
        ≠
每个业务任务都通过
```

输入不满足变量要求的案例还可能被过滤掉。比较界面默认展示基线案例范围，也不意味着双方一定拥有同样的有效样本集合。

实际验收应检查：原定案例数、被过滤数、有运行证据的案例数、执行错误数、有评分数、未评分数，再看得分和成本。

另一个版本边界是：当前 v2 observation 裁判在 worker 领取任务时解析版本，并记录实际执行版本，而非一入队就冻结。对于在线运行，这允许配置及时生效；对于严格回归，需要核对实际裁判版本，不能只凭实验启动时的配置推断。

数据集版本也只固定案例数据，不会自动冻结外部工具数据、模型服务或业务环境。部分配置失败处理路径与正常路径的版本查询行为还存在差异，不能把“支持版本”扩大成所有路径的完整快照保证。

### 13. 线上问题怎样变成下一轮回归？

它有实际的“将 observations 加入 dataset”批处理实现：

1. 筛选或选择问题观测。
2. 配置 input、expectedOutput、metadata 的字段映射。
3. 预览并校验映射。
4. 创建批任务，固定筛选边界。
5. 后台逐条映射并创建 dataset items。
6. 保存 sourceTraceId/sourceObservationId。
7. 返回创建数量和映射、校验失败信息。

人工可以先判断 Agent 是否确实出错，再修正标准答案，加入回归集。

```text
线上低分或用户反馈
        ↓
打开原始 trace 与裁判 trace
        ↓
人工确认问题类型
        ↓
修正期望或评分标准
        ↓
加入带来源引用的数据集
        ↓
新旧方案运行同一批案例
        ↓
检查旧问题是否修好、是否引入新退化
```

这是它最有价值的产品流程：真实问题不会只停留在日志里，而是有机会变成持续验证的案例资产。

不过，把线上结果映射为 expectedOutput 只是数据搬运能力。坏答案不会因为进入数据集就自动变成好答案。

源码：[映射交互说明](../../../langfuse/web/src/features/batch-actions/components/AddObservationsToDatasetDialog/README.md)、[后台转换](../../../langfuse/worker/src/features/batchAction/processAddObservationsToDataset.ts)。

### 14. 出现问题时，按什么顺序定位？

下面是利用这些证据进行排查的顺序，不代表 Langfuse 已自动完成全部根因分析。

| 现象 | 先查看什么 | 下一步判断 |
| --- | --- | --- |
| 案例没有执行记录 | 数据集版本、ACTIVE 状态、输入变量、远程触发结果 | 是没被选中，还是外部执行器没有运行 |
| 有业务 trace，没有评分任务 | Rule、过滤、采样、assignment、内部环境排除 | 是否应该被评分 |
| 任务长时间等待 | worker、队列、DELAYED 状态、Provider 错误 | 是服务等待还是重试 |
| 任务 ERROR，没有 Score | 错误原因和裁判 trace | 先修输入、配置或基础设施 |
| 正常评分但分数明显不合理 | 映射后输入、expectedOutput、rubric、实际裁判版本 | 是映射错、标准错还是模型误判 |
| 工具结果正确，最终回答错误 | 实际给模型的上下文与回答步骤 | Agent 是否遗漏或误解证据 |
| Agent 说修改成功，业务实际没改 | 工具回执、外部状态查询、确定性 grader | 是否缺失业务状态验证 |
| 新版本均分高，但某些用户更差 | 同题对照、案例分组、缺失项 | 查退化分布，避免均值掩盖 |
| 已 COMPLETED，界面暂时没分数 | score ingestion 与查询延迟 | 区分异步可见性和真正丢失 |

例如，“地址修改正确却得零分”可以这样查：

```text
业务状态证据是否真的正确？
        ↓
裁判是否收到正确的订单与地址字段？
        ↓
expectedOutput 是否仍是旧地址？
        ↓
裁判提示词是否把某个非必要字段设成硬要求？
        ↓
实际裁判版本与上次是否一致？
        ↓
裁判返回了什么理由？
```

这里的价值在于缩小问题范围。只保存一个零分，就无法进行这样的分析。

### 15. 它自己的机制怎样验证？

相关测试源码覆盖了不少工程约束，例如：

- 不匹配或未采样的数据不上传评分输入。
- 多规则命中时复用同一份观测数据。
- 多个 evaluator assignment 正确展开。
- 相同 observation ID 在不同 trace 下不发生任务身份冲突。
- 规则停用或 assignment 删除后取消执行。
- 输入下载失败与输入格式无效采用不同重试语义。
- LLM 与代码裁判接入共同完成逻辑。
- 实验调度、字段映射与版本查询等路径。

这些测试验证评测平台的实现行为，不能替代对业务评分标准的校准。业务上仍要用已知正例、已知反例、人工标注和边界案例，确认裁判真的在评估想要的能力。

测试入口：[调度测试](../../../langfuse/worker/src/features/evaluation/observationEval/__tests__/scheduleObservationEvals.test.ts)、[执行器测试](../../../langfuse/worker/src/features/evaluation/observationEval/__tests__/observationEvalProcessor.test.ts)、[实验测试](../../../langfuse/worker/src/__tests__/experimentsService.test.ts)。这里只说明源码中存在的覆盖，不表示本次已经运行通过。

### 16. 哪些做法最值得我们借鉴？

**第一，评分结果同时关联两份证据。** 一份说明 Agent 做了什么，另一份说明裁判为什么这样判断。这样才能区分业务退化与评分系统变化。

**第二，规则与裁判分离。** 用户配置评谁、抽多少、什么时候评；裁判专注如何判断。同一裁判不必为每个工具重写一遍接入逻辑。

**第三，把执行状态与业务分数分开。** 零分、未评分、评分错误、评分等待是不同事实，报告必须分别呈现。

**第四，让真实失败进入版本化回归集。** 保留来源引用和人工修正后的期望，下一轮能直接验证同一个问题，而不是靠人记住曾经出现过什么。

**第五，比较必须落到具体案例。** 平均分只是入口，逐项输出、轨迹、成本与分数才解释得了改动的收益与代价。

**第六，给通用平台划清边界。** Langfuse 没有替用户定义所有业务成功条件，也没有在这些评测路径里替我们实现 Runtime 的宕机、审批恢复和副作用故障注入。我们的执行与故障机制仍有独立价值。

OpenViking 更值得借鉴的是如何设计受控能力实验、分开验证动作与信息完整性；Langfuse 更值得借鉴的是如何把观测、裁判、人工复核和回归实验组织成可持续使用的平台流程。SeekFlux 可以同时吸收这两部分，让使用者提供业务环境与成功条件，由公共模块承担执行生命周期、证据、故障、评分和对照。
